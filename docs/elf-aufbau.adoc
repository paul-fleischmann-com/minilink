= Aufbau einer ELF64-Datei
:toc: left
:toclevels: 3
:sectnums:
:icons: font
:source-highlighter: rouge

Dieses Dokument beschreibt den Aufbau einer ELF64-Datei so weit, wie er
für `minilink` (siehe `../README.md`) relevant ist: relozierbare
Objektdateien (`ET_REL`, die Eingabe) und statische Executables
(`ET_EXEC`, die Ausgabe). Dynamisches Linken, Archive und die meisten
optionalen Sections bleiben bewusst außen vor.

Referenz-Header ist die System-`elf.h` (`/usr/include/elf.h`), aus der
`minilink` alle Strukturen und Konstanten bezieht.

== Die zwei Sichten auf eine ELF-Datei

ELF kennt zwei sich überlagernde Gliederungen desselben Bytestroms:

[cols="1,3,3",options="header"]
|===
| Sicht | Beschreibung | Beschrieben durch

| *Linking View*
| Was der Linker sieht: einzelne _Sections_ (`.text`, `.data`,
  `.symtab`, `.rela.text` …), Symbole, Relocations.
| *Section Header Table* (SHT)

| *Execution View*
| Was der Kernel/Loader beim Programmstart sieht: wenige _Segments_,
  die in den Adressraum gemappt werden (Code R-X, Daten RW …).
| *Program Header Table* (PHT)
|===

* Eine Objektdatei (`ET_REL`) hat **nur** einen sinnvollen Linking View
  — keine Program Header. `minilink` liest genau diesen View.
* Ein Executable (`ET_EXEC`) hat **immer** einen Execution View und
  meist zusätzlich noch einen Linking View. `minilink` schreibt bewusst
  nur den Execution View (2 Segmente) und lässt die Section Header weg —
  der Kernel braucht sie zum Ausführen nicht.

.Gesamtlayout (schematisch)
----
  niedrige Datei-Offsets
  ┌───────────────────────────┐  Offset 0
  │  ELF-Header (Elf64_Ehdr)  │  64 Bytes, immer am Anfang
  ├───────────────────────────┤
  │  Program Header Table     │  nur bei ausführbaren / .so-Dateien
  │  (Array aus Elf64_Phdr)   │  Position: e_phoff
  ├───────────────────────────┤
  │                           │
  │  Section-Inhalte:         │
  │   .text  (Code)           │
  │   .rodata (Konstanten)    │
  │   .data  (init. Daten)    │
  │   .bss   (0 Bytes im File)│  SHT_NOBITS: belegt keinen Platz
  │   .symtab / .strtab       │
  │   .rela.text / .rela.data │
  │   .shstrtab               │
  │   ...                     │
  │                           │
  ├───────────────────────────┤
  │  Section Header Table     │  Array aus Elf64_Shdr
  │  (Array aus Elf64_Shdr)   │  Position: e_shoff
  └───────────────────────────┘
  hohe Datei-Offsets
----

NOTE: Die Reihenfolge "Header, dann PHT, dann Daten, dann SHT" ist
üblich, aber nicht vorgeschrieben. Verbindlich ist nur: der ELF-Header
liegt bei Offset 0, alles andere wird über Offsets im Header gefunden.

== Der ELF-Header (`Elf64_Ehdr`)

Immer 64 Byte, immer bei Offset 0. Er ist der Einstiegspunkt: jede
andere Struktur wird über ein Feld hier lokalisiert.

[cols="1,1,4",options="header"]
|===
| Feld | Größe | Bedeutung

| `e_ident[16]`   | 16 B | Magic + Format-Grunddaten, siehe unten
| `e_type`        | 2 B  | Dateityp: `ET_REL`=1 (Objekt), `ET_EXEC`=2 (statisches Executable), `ET_DYN`=3 (PIE / Shared Object), `ET_CORE`=4
| `e_machine`     | 2 B  | Ziel-ISA: `EM_X86_64`=62 (0x3e)
| `e_version`     | 4 B  | immer `EV_CURRENT`=1
| `e_entry`       | 8 B  | virtuelle Einsprungadresse (nur Executable); bei `ET_REL` = 0
| `e_phoff`       | 8 B  | Datei-Offset der Program Header Table (0 = keine)
| `e_shoff`       | 8 B  | Datei-Offset der Section Header Table (0 = keine)
| `e_flags`       | 4 B  | prozessorspezifische Flags (x86-64: 0)
| `e_ehsize`      | 2 B  | Größe dieses Headers (64)
| `e_phentsize`   | 2 B  | Größe eines Program-Header-Eintrags (56)
| `e_phnum`       | 2 B  | Anzahl Program-Header-Einträge
| `e_shentsize`   | 2 B  | Größe eines Section-Header-Eintrags (64)
| `e_shnum`       | 2 B  | Anzahl Section-Header-Einträge
| `e_shstrndx`    | 2 B  | Index der Section, die die *Section-Namen* enthält (`.shstrtab`)
|===

=== `e_ident` im Detail

[cols="1,2,4",options="header"]
|===
| Index | Name | Wert

| 0..3 | `EI_MAG0..3`   | `0x7F`, `'E'`, `'L'`, `'F'`  (`\x7fELF`)
| 4    | `EI_CLASS`     | `ELFCLASS32`=1 / `ELFCLASS64`=2
| 5    | `EI_DATA`      | `ELFDATA2LSB`=1 (little endian) / `ELFDATA2MSB`=2
| 6    | `EI_VERSION`   | `EV_CURRENT`=1
| 7    | `EI_OSABI`     | `ELFOSABI_SYSV`=0 (Linux setzt meist 0)
| 8    | `EI_ABIVERSION`| 0
| 9..15| Padding        | 0
|===

`minilink` prüft in `load_object_file()` genau zwei Dinge:
`memcmp(e_ident, ELFMAG, 4) == 0` und `e_type == ET_REL`.

.Beispiel: Hex-Dump des Headers von `test/main.o`
[source]
----
0000: 7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
      └─ELF──┘  │  │  │
                │  │  └─ EI_VERSION = 1
                │  └──── EI_DATA    = 1  (little endian)
                └─────── EI_CLASS   = 2  (64 bit)
0010: 01 00 3e 00 01 00 00 00 00 00 00 00 00 00 00 00
      └─┬─┘ └─┬─┘ └────┬────┘ └──────── e_entry = 0 ──────
      e_type e_machine e_version
       =1     =0x3e      =1
       ET_REL EM_X86_64
0020: 00 00 00 00 00 00 00 00 b8 02 00 00 00 00 00 00
      └── e_phoff = 0 ──────┘ └── e_shoff = 0x2b8 = 696 ─
0030: 00 00 00 00 40 00 00 00 00 00 40 00 0c 00 0b 00
      └e_flags┘ └ehsz┘ └phes┘ └phn┘ └shes┘ │ shnum │ shstrndx
              =0    =64    =0    =0    =64  =12       =11
----

== Sections (Linking View)

Eine Section ist ein benannter, typisierter Byte-Bereich. Beschrieben
wird jede durch einen `Elf64_Shdr`-Eintrag in der Section Header Table
(`e_shoff`, `e_shnum` Einträge à 64 Byte). Section 0 ist immer ein
Null-Eintrag (`SHT_NULL`).

.`Elf64_Shdr`
[cols="1,1,4",options="header"]
|===
| Feld | Größe | Bedeutung

| `sh_name`      | 4 B | Offset in `.shstrtab` → Section-Name als C-String
| `sh_type`      | 4 B | siehe Tabelle unten
| `sh_flags`     | 8 B | `SHF_WRITE`=0x1, `SHF_ALLOC`=0x2 (belegt Speicher zur Laufzeit), `SHF_EXECINSTR`=0x4
| `sh_addr`      | 8 B | virtuelle Adresse zur Laufzeit (bei `ET_REL` = 0, wird vom Linker vergeben)
| `sh_offset`    | 8 B | Datei-Offset der Section-Bytes (bei `SHT_NOBITS` bedeutungslos)
| `sh_size`      | 8 B | Größe in Bytes (bei `.bss` > 0, obwohl 0 Bytes im File)
| `sh_link`      | 4 B | Index einer verknüpften Section (Bedeutung je `sh_type`)
| `sh_info`      | 4 B | Zusatzinfo (Bedeutung je `sh_type`)
| `sh_addralign` | 8 B | geforderte Ausrichtung (Zweierpotenz; 0/1 = keine)
| `sh_entsize`   | 8 B | Größe eines Eintrags bei Tabellen-Sections (`.symtab`: 24), sonst 0
|===

.Wichtige `sh_type`-Werte
[cols="1,1,4",options="header"]
|===
| Konstante | Wert | Inhalt

| `SHT_NULL`     | 0  | ungenutzter Eintrag (Index 0)
| `SHT_PROGBITS` | 1  | konkrete Bytes aus dem Programm (`.text`, `.rodata`, `.data`, …)
| `SHT_SYMTAB`   | 2  | Symboltabelle (`.symtab`)
| `SHT_STRTAB`   | 3  | Stringtabelle (`.strtab`, `.shstrtab`)
| `SHT_RELA`     | 4  | Relocations *mit* Addend (`.rela.text`, …)  — x86-64 nutzt immer RELA
| `SHT_NOBITS`   | 8  | belegt Laufzeitspeicher, aber keinen Platz im File (`.bss`)
| `SHT_REL`      | 9  | Relocations *ohne* Addend (auf x86-64 unüblich)
|===

=== Die Sections, die `minilink` verarbeitet

`classify_section()` in `src/minilink.c` teilt jede Section anhand ihres
Namens in vier Klassen ein, alles andere wird ignoriert:

[cols="1,1,1,3",options="header"]
|===
| Name-Präfix | Klasse | Ziel-Segment | Inhalt

| `.text`   | Code       | R-X | Maschinencode
| `.rodata` | Konstanten | RW (bei minilink) | String-Literale, `const`-Daten
| `.data`   | Daten      | RW  | initialisierte globale/statische Variablen
| `.bss`    | Daten      | RW  | mit 0 initialisierte Variablen (`SHT_NOBITS`)
|===

Ignoriert werden u. a. `.eh_frame`, `.comment`, `.note.*` sowie alle
`.debug_*`-Sections — für die reine Ausführung nicht nötig.

== Die Symboltabelle (`.symtab` + `.strtab`)

`.symtab` ist ein Array aus `Elf64_Sym` (je 24 Byte). Der Section-Header
von `.symtab` verweist per `sh_link` auf die zugehörige `.strtab`
(Symbolnamen) und per `sh_info` auf den Index des ersten globalen
Symbols (alle davor sind lokal).

.`Elf64_Sym`
[cols="1,1,4",options="header"]
|===
| Feld | Größe | Bedeutung

| `st_name`  | 4 B | Offset in `.strtab` → Symbolname (0 = namenlos)
| `st_info`  | 1 B | Bindung (obere 4 Bit) + Typ (untere 4 Bit), siehe unten
| `st_other` | 1 B | Sichtbarkeit (`STV_DEFAULT` … ), von minilink ignoriert
| `st_shndx` | 2 B | Index der definierenden Section; `SHN_UNDEF`=0 → *undefiniert* (extern); `SHN_ABS`=0xfff1 → absoluter Wert
| `st_value` | 8 B | bei `ET_REL`: Offset *innerhalb* `st_shndx`; bei `ET_EXEC`: finale virtuelle Adresse
| `st_size`  | 8 B | Größe des Objekts/der Funktion (informativ)
|===

.Bindung — `ELF64_ST_BIND(st_info)`
[cols="1,1,4",options="header"]
|===
| Konstante | Wert | Bedeutung

| `STB_LOCAL`  | 0 | nur in dieser Datei sichtbar; Name darf mehrfach vorkommen
| `STB_GLOBAL` | 1 | dateiübergreifend sichtbar; Mehrfachdefinition = Fehler
| `STB_WEAK`   | 2 | wie global, aber überschreibbar; von minilink nicht gesondert behandelt
|===

.Typ — `ELF64_ST_TYPE(st_info)`
[cols="1,1,4",options="header"]
|===
| Konstante | Wert | Bedeutung

| `STT_NOTYPE`  | 0 | untypisiert (typisch für externe Referenzen)
| `STT_OBJECT`  | 1 | Datenobjekt (Variable)
| `STT_FUNC`    | 2 | Funktion
| `STT_SECTION` | 3 | steht für den Anfang einer Section; von Relocations genutzt, die section-relativ adressieren
| `STT_FILE`    | 4 | Quelldateiname; von minilink übersprungen
|===

`import_symbols()` in `src/minilink.c`:

* `STT_FILE` wird übersprungen.
* `STT_SECTION` bekommt einen synthetischen Namen `<section:.rodata>`,
  damit die Relocation-Phase es wiederfindet.
* `st_shndx == SHN_UNDEF` → Symbol als _undefiniert_ merken, Auflösung
  später in `resolve_all_symbols()` gegen alle anderen Dateien.
* Zwei `STB_GLOBAL`-Definitionen desselben Namens → sofortiger Abbruch
  ("multiple definition").

== Relocations (`.rela.<section>`)

Ein Relocation-Eintrag sagt: „an Offset _X_ in Section _S_ muss ein
Wert eingesetzt werden, der von Symbol _Sym_ und einem konstanten
Addend abhängt". Solange der Linker die finalen Adressen nicht kennt,
stehen dort Platzhalter (meist 0).

Auf x86-64 immer `SHT_RELA` (mit explizitem Addend), Struktur
`Elf64_Rela` (24 Byte):

[cols="1,1,4",options="header"]
|===
| Feld | Größe | Bedeutung

| `r_offset` | 8 B | Offset der Patch-Stelle innerhalb der Ziel-Section
| `r_info`   | 8 B | oben: Symbolindex (`ELF64_R_SYM`), unten: Typ (`ELF64_R_TYPE`)
| `r_addend` | 8 B | konstanter Summand _A_
|===

Der Section-Header der `.rela.text` verweist per `sh_info` auf die
Section, die gepatcht wird (`.text`), und per `sh_link` auf `.symtab`.

.Von `minilink` unterstützte Typen (`apply_relocations()`)
[cols="1,1,3,3",options="header"]
|===
| Typ | Wert | Formel | Verwendung

| `R_X86_64_64`   | 1  | `S + A`         | absoluter 64-Bit-Zeiger (z. B. in `.data`)
| `R_X86_64_PC32` | 2  | `S + A - P`     | PC-relativer 32-Bit-Bezug (`lea`, `mov` rel. RIP)
| `R_X86_64_PLT32`| 4  | `S + A - P`     | `call`/`jmp` über PLT — ohne dyn. Linken wie `PC32`
| `R_X86_64_32`   | 10 | `S + A` (zero-ext) | absolute 32-Bit-Referenz
| `R_X86_64_32S`  | 11 | `S + A` (sign-ext) | absolute 32-Bit-Referenz, vorzeichenbehaftet
|===

Dabei ist:

* *S* = finale Adresse des Symbols (`Sym.final_address` nach Placement)
* *A* = `r_addend`
* *P* = finale Adresse der Patch-Stelle selbst
  (`section_base + merged_offset + r_offset`)

Bei den 32-Bit-Typen prüft `minilink`, ob das Ergebnis in einen
`int32_t` passt, und bricht sonst ab.

== Program Header Table (Execution View)

Nur in `ET_EXEC`/`ET_DYN`. Array aus `Elf64_Phdr` (je 56 Byte) ab
`e_phoff`, `e_phnum` Einträge. Jeder Eintrag beschreibt ein Segment —
einen Bereich, den der Kernel beim `execve()` in den Adressraum mappt.

.`Elf64_Phdr`
[cols="1,1,4",options="header"]
|===
| Feld | Größe | Bedeutung

| `p_type`   | 4 B | `PT_LOAD`=1 (mappbares Segment), `PT_DYNAMIC`=2, `PT_INTERP`=3, `PT_GNU_STACK`=0x6474e551 …
| `p_flags`  | 4 B | `PF_X`=1, `PF_W`=2, `PF_R`=4 (bitweise oder)
| `p_offset` | 8 B | Datei-Offset des Segmentinhalts
| `p_vaddr`  | 8 B | virtuelle Zieladresse
| `p_paddr`  | 8 B | physische Adresse (auf Linux irrelevant, = `p_vaddr`)
| `p_filesz` | 8 B | Bytes im File
| `p_memsz`  | 8 B | Bytes im Speicher; `p_memsz > p_filesz` → Rest wird mit 0 gefüllt (so entsteht `.bss`)
| `p_align`  | 8 B | Ausrichtung; `p_offset` ≡ `p_vaddr` (mod `p_align`)
|===

=== Das Layout, das `minilink` schreibt

`write_output()` erzeugt genau zwei `PT_LOAD`-Segmente:

[cols="1,2,2,2",options="header"]
|===
| Segment | Flags | Inhalt | virtuelle Basis

| Code   | `PF_R \| PF_X` | ELF-Header + PHT + `.text` | `0x400000`
| Daten  | `PF_R \| PF_W` | `.rodata` + `.data` (+ `.bss` nur in `memsz`) | nächste Page nach `.text`
|===

.Fester Adressraum-Plan
----
  0x400000  ┌─────────────────────────────┐  ─┐
            │ ELF-Header + Program-Header  │   │  Segment 1 (R-X)
  0x401000  │ .text                        │   │  p_filesz = p_memsz
            │                             │  ─┘
  0x402000  ┌─────────────────────────────┐  ─┐
            │ .rodata                     │   │  Segment 2 (RW)
            │ .data                       │   │  p_filesz  = rodata+data
            ├─────────────────────────────┤   │  p_memsz   = + .bss
            │ .bss  (nur im Speicher,     │   │
            │        0 Bytes im File)     │  ─┘
            └─────────────────────────────┘
----

Section Header werden nicht geschrieben (`e_shoff = 0`, `e_shnum = 0`) —
der Kernel braucht zum Laden nur die Program Header.

== Ablauf in `minilink` — von ELF zu ELF

[cols="1,3,3",options="header"]
|===
| Stufe | Funktion(en) | ELF-Bezug

| 1 Reader
| `load_object_file`, `import_sections`, `import_symbols`, `import_relocations`
| `Elf64_Ehdr` prüfen; `Elf64_Shdr[]` klassifizieren; `Elf64_Sym[]` + `.strtab` einlesen; `Elf64_Rela[]` sammeln

| 2 Resolver
| `resolve_all_symbols`
| jedes `SHN_UNDEF`-Symbol gegen die globalen Definitionen aller Dateien auflösen

| 3 Merger
| `import_sections` (Sammeln) + `place_sections`
| gleichnamige Sections aller Dateien aneinanderhängen, `sh_addralign` beachten

| 4 Locator
| `place_sections`, `assign_symbol_addresses`
| virtuelle Adressen vergeben → `st_value` wird zur finalen Adresse

| 5 Relocation
| `apply_relocations`
| `Elf64_Rela`-Einträge nach den Formeln oben in die Section-Bytes patchen

| 6 Writer
| `write_output`
| neuen `Elf64_Ehdr` (`ET_EXEC`) + 2× `Elf64_Phdr` + Section-Bytes schreiben
|===

== Nützliche Werkzeuge zum Gegenprüfen

[cols="2,3",options="header"]
|===
| Kommando | Zeigt

| `readelf -h datei.o`        | ELF-Header
| `readelf -S datei.o`        | Section Header Table
| `readelf -s datei.o`        | Symboltabelle
| `readelf -r datei.o`        | Relocations
| `readelf -l programm`       | Program Header / Segmente
| `objdump -d datei.o`        | Disassembly von `.text`
| `xxd datei.o \| head`       | roher Hex-Dump
|===
